# Document Organization --- v0.1 Completion & Project Integration Summary

## 1. Executive Summary

### What

The **Document Organization** feature is the third major processing
capability developed for DocuMate's construction document management
pipeline.

Its purpose is to take the structured information produced by **Document
Intelligence** and use it to:

-   determine how a document should be categorized,
-   generate a standardized filename,
-   determine the appropriate project folder structure,
-   create the required directories,
-   move the physical document into the organized location, and
-   record the organization result through the existing processing
    pipeline.

The feature was developed as **Document Organization v0.1**, with a
deliberately simple and configurable rule-based approach.

### Why

Construction project documents are commonly uploaded with inconsistent
filenames and are often stored in unstructured locations. Even after OCR
and document intelligence identify what a document contains, the
document still needs to be placed somewhere meaningful.

The Organization feature closes that gap.

The overall responsibility of the AI pipeline is separated into three
clear questions:

``` text
OCR
What text exists?

        ↓

Document Intelligence
What does the document represent?

        ↓

Document Organization
Where and how should the document live?
```

### How

The feature receives the structured `DocumentIntelligenceResult`
generated by the previous stage.

It then:

1.  Determines the organization category.
2.  Determines the target directory.
3.  Generates a standardized filename.
4.  Produces an organization result.
5.  Passes that result to the file organizer.
6.  Creates the required directory structure.
7.  Moves the physical file.
8.  Handles duplicate filenames using suffixes such as `_1`, `_2`, etc.
9.  Returns the final organized path to the processing pipeline.
10. Logs the organization result and completion status.

For v0.1, organization is performed on the **local filesystem**.

## 2. High-Level Technical Implementation

### Technology Used

-   Python
-   Django
-   Pydantic
-   Existing `Document` and `DocumentIntelligence` models
-   Existing `ProcessingManager`
-   Local filesystem
-   Python `pathlib`
-   Python logging

No new database was introduced for the Organization feature.

The existing `DocumentIntelligence` record and `ProcessingLog`
infrastructure are reused.

### Component Structure

``` text
ai_processing/
├── services/
│   └── organization_service.py
├── engines/
│   └── organization_engine.py
├── organizers/
│   └── file_organizer.py
├── schemas/
│   └── organization_schema.py
└── utils/
    └── filename_utils.py
```

### Organization Schema

The schema represents the decision made by the organization layer. It
contains information such as:

-   `target_directory`
-   `target_filename`
-   `target_path`
-   `organization_category`
-   `organization_reason`
-   `status`

This provides a clear boundary between the organization decision and the
physical file operation.

### Organization Engine

The `OrganizationEngine` transforms:

``` text
DocumentIntelligenceResult
        ↓
OrganizationResult
```

It decides:

-   document category,
-   target directory,
-   standardized filename.

It does **not** physically move files.

### File Organizer

The `FileOrganizer` handles the physical filesystem operation:

-   creates missing directories,
-   moves the source document,
-   prevents accidental overwrites,
-   handles duplicate filenames,
-   returns the final physical path.

Example:

``` text
ABC_Tower/
└── Architectural/
    └── Drawings/
        └── A-101_Ground_Floor_Plan_R02.pdf
```

Duplicate handling:

``` text
A-101_Ground_Floor_Plan_R02.pdf
A-101_Ground_Floor_Plan_R02_1.pdf
A-101_Ground_Floor_Plan_R02_2.pdf
```

### Organization Service

`OrganizationService` is the integration boundary between the processing
pipeline and the organization components.

``` text
Document
    +
DocumentIntelligence
        ↓
OrganizationEngine
        ↓
OrganizationResult
        ↓
FileOrganizer
        ↓
Final Organized File
```

## 3. Organization Rules --- v0.1

### Filename Rules

For drawings:

``` text
{drawing_number}_{drawing_title}_{revision}.{extension}
```

Example:

``` text
A-101_Ground_Floor_Plan_R02.pdf
```

If revision or drawing number is unavailable, the missing component is
omitted.

For non-drawing documents:

``` text
{document_type}_{document_name}.{extension}
```

Unsafe characters and spaces are normalized.

### Folder Structure

The general structure is:

``` text
{Project}/{Discipline or Category}/{Document Type}
```

Example:

``` text
ABC_Tower/
├── Architectural/
│   ├── Drawings/
│   └── Specifications/
├── Structural/
│   ├── Drawings/
│   └── Reports/
├── Electrical/
│   └── Drawings/
└── Mechanical/
    └── Drawings/
```

The taxonomy is intentionally limited and configurable in v0.1.

### Fallback Behavior

Incomplete metadata does not automatically fail organization.

Fallbacks such as:

``` text
Unclassified/
```

are used when information cannot be mapped to a known category.

Missing drawing numbers or revisions are omitted rather than causing
failure.

### Architectural Boundary

``` text
┌──────────────────────────────┐
│          OCR Service         │
│                              │
│ Extract text from document   │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│    Document Intelligence     │
│                              │
│ Understand document meaning  │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│    Document Organization     │
│                              │
│ Decide where/how to store    │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│       File Organizer         │
│                              │
│ Perform physical file move   │
└──────────────────────────────┘
```

The modules remain loosely coupled.

### ProcessingManager Integration

The central pipeline is now:

``` text
ProcessingManager
       │
       ├── OCRService
       ├── IntelligenceService
       └── OrganizationService
```

Each service follows the common processing contract and returns a
`ProcessingResult`.

The manager provides:

-   stage lifecycle logging,
-   execution-time measurement,
-   `ProcessingLog` creation,
-   failure handling,
-   processing status updates.

### Complete Processing Flow

``` text
Portal Upload
      ↓

      ↓
DocumentIntelligence created
      ↓
ProcessingManager
      ↓
OCRService
      ↓
OCRResult
      ↓
IntelligenceService
      ↓
DocumentIntelligenceResult
      ↓
OrganizationService
      ↓
OrganizationEngine
      ↓
OrganizationResult
      ↓
FileOrganizer
      ↓
Organized File
      ↓
ProcessingManager
      ↓
SUCCESS
```

## 6. Testing and Validation

The Organization module was tested independently before portal
integration.

Coverage included:

-   organization schema validation,
-   architectural drawings,
-   structural drawings,
-   electrical drawings,
-   mechanical drawings,
-   drawings without revision,
-   drawings without drawing number,
-   drawings without both number and revision,
-   reports,
-   specifications,
-   unknown document types,
-   empty intelligence,
-   filename normalization,
-   file movement,
-   directory creation,
-   duplicate filenames,
-   multiple duplicates,
-   missing source files,
-   service-to-engine-to-organizer integration.

An early path portability issue was identified where logical
organization paths used Windows separators:

``` text
ABC_Tower\Unclassified\Specifications
```

instead of:

``` text
ABC_Tower/Unclassified/Specifications
```

The fix separated the concerns:

-   organization results use portable `/` path representation,
-   `FileOrganizer` handles OS-specific filesystem operations.

## 9. Post-v0.1 Status and Future Improvements

The current implementation intentionally remains at a practical v0.1
level.

Some documents may still be placed under:

``` text
Unclassified/
```

This is currently acceptable for v0.1. The system uses available
metadata and falls back safely instead of failing the processing
pipeline.

### Potential v0.2 Improvements

Deferred improvements include:

-   more comprehensive construction document taxonomy,
-   improved document-type mapping,
-   better handling of classification variations,
-   more precise discipline detection,
-   improved fallback categories,
-   document-specific organization rules,
-   more advanced filename strategies,
-   semantic duplicate detection,
-   content-based duplicate detection,
-   human review for low-confidence classifications,
-   cloud storage support,
-   asynchronous processing,
-   organization analytics,
-   configurable project-specific folder structures.

These should only be introduced when actual requirements justify them.
